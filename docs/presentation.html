Architecture: store R4 once, serve R4 and R6

Every resource is stored as FHIR R4 in PostgreSQL 18. /R4 reads and writes it directly. /R6 runs FHIR Mapping Language (FML) maps over the same rows: R4 → R6 on every read, R6 → R4 on writes where a reverse map exists (BodyStructure).

WatchWhat the generated map does not read

The map header lists R4 elements with no rule: statusHistory, classHistory, reasonCode, reasonReference, diagnosis.rank, and three hospitalization lists (dietPreference, specialCourtesy, specialArrangement). Case 2 / 3 · Search · 4 / 7

Encounter: searching by class in both versions

The stored row has class AMB natively and VR in the cross-version extension. R4 class keeps its standard meaning, because R4 doesn't allow redefining a standard parameter. R6 class sees the whole list. class-r6 gives R4 clients the R6 behaviour under its own name.

The calls (searching for this encounter)

GET/R4/Encounter?class=…|AMB200found, R4
GET/R4/Encounter?class=…|VR200not found (total 0)
GET/R4/Encounter?class-r6=…|VR200found, R4: class object + extension
GET/R6/Encounter?class=…|VR200found, R6: class list, no extension
GET/R6/Encounter?class=…|AMB200found, R6
GET/R4/Encounter?class=…&class-r6=…400“Combining class and class-r6 is not supported”
GET/R6/Encounter?class-r6=…400“Unsupported search parameter: class-r6”

… = http://terminology.hl7.org/CodeSystem/v3-ActCode. Accepted token forms: code, system|code, |code, system|. No modifiers, lists or paging yet.

R4How we implemented it: a SearchParameter definition

GET /R4/SearchParameter/Encounter-class-r6

{
  "resourceType": "SearchParameter",
  "id": "Encounter-class-r6",
  "url": "http://example.org/fhir/SearchParameter/Encounter-class-r6",
  "name": "EncounterClassR6",
  "derivedFrom": "http://hl7.org/fhir/SearchParameter/Encounter-class",
  "status": "draft",
  "description": "Backport of the R6 Encounter `class` search to R4. …",
  "code": "class-r6",
  "base": ["Encounter"],
  "type": "token",
  "expression": "Encounter.class
     | Encounter.extension('http://hl7.org/fhir/6.0/StructureDefinition/
                            extension-Encounter.class').value",
  "multipleOr": false,
  "multipleAnd": false
}
  • Lives in fhir/r4/, a small local FHIR package that the canonical manager loads next to hl7.fhir.r4.core. getSearchParametersForResource("Encounter") now returns it with the 22 core parameters.
  • The R4 CapabilityStatement points class-r6 at this url, and the server serves the resource, so the link resolves.
  • The search itself is still Patrick's SQL over the stored R4, which matches this expression. /R6 runs each hit through Encounter4to6.

WatchDecisions and open questions

  • Why a new name: R4 class must keep its standard meaning, so the backport can't reuse the name. The name class-r6 follows a pattern we could use for other changed elements.
  • Canonical URL: example.org is a placeholder until we have a namespace of our own. It isn't under hl7.org, because HL7 publishes no such parameter.
  • What the extension holds: HL7 doesn't say whether it carries all classes or only the extra ones. We assume only the extra ones, so an extension that repeats the native class shows up twice in R6.
  • No data migration: rows saved with the old xver/encounter-class URL are no longer searched or mapped. Checked on the earlier Encounter cc094385-…: its R6 class now holds only AMB, and VR comes through as a plain extension.
  • Generator follow-up: the filter that stops 6.0 cross-version extensions being copied into R6 is a local edit to three generated maps, and still needs to go into the map generator.

Case 3 / 3 · 5 / 7

BodyStructure: one R6 resource, several R4 rows

R6 includedStructure repeats (1..*), but R4 has one location and one morphology. So an R6 BodyStructure is written as one R4 row per structure: <id>, <id>--2, …. R6-only values live in R4 extensions. This is the one type with writes through /R6, using hand-written maps in both directions.

The calls

POST/R6/BodyStructure2012 structures → 2 R4 rows
GET/R4/BodyStructure/452142f2-…200row 1 (primary): forearm
GET/R4/BodyStructure/452142f2-…--2200row 2: humerus
PUT/R4/BodyStructure/452142f2-…--2200R4 client edits description on row 2
GET/R6/BodyStructure/452142f2-…200versionId 2, new description, both structures intact

Each write rewrites the whole group in one transaction. It commits only if every row is valid R4 and the group converts back to valid R6 without losing anything; otherwise 422.

FMLBodyStructure_6to4.fml (hand-written)

group BodyStructureSplit(source src : BodyStructureR6,
                         target bundle : BundleR4) {
  src.includedStructure as inc
    -> create('BodyStructure') as out,
       bundle.entry as e, e.resource = out
    then BodyStructureRow(src, inc, out);   // 1 row each
}

group BodyStructureRow(source src, source inc,
                       target out) {
  src.description -> out.description; // shared,
  src.patient     -> out.patient;     // every row
  inc.structure -> out.location;
  inc.morphology first -> out.morphology;
  inc.morphology not_first as v
    -> out.extension as x,
       x.url = '…/extension-BodyStructure
                 .includedStructure.morphology',
       x.valueCodeableConcept as t
    then CodeableConcept(v, t);
  inc.laterality as v -> out.locationQualifier as q
    then MarkLaterality(v, q);  // + marker ext
  … qualifier, excludedStructure, landmarks,
    spatialReference, image, origin → extensions
}

The reverse map, BodyStructure_4to6.fml, merges the rows back: the first row gives the shared fields, and each row adds one includedStructure.

Case 3 / 3 · References · 6 / 7

BodyStructure: splitting breaks references

Splitting one R6 BodyStructure into R4 rows gives it two identities: R4 clients see rows (99dc…--2), R6 clients see one resource (99dc…). Every resource that points at a BodyStructure has to be translated between the two, and kept valid when rows move. Artur's PR #6 does this for Observation.

The calls

POST/R6/BodyStructure2013 structures → rows 99dc…, --2, --3
POST/R4/Observation201o1: bodySite extension → BodyStructure/99dc…--2
POST/R4/Observation201o2: references --2 and --3
GET/R6/Observation/o1200bodyStructure → BodyStructure/99dc…
GET/R6/Observation/o2200one entry, not two
GET/R4/BodyStructure/99dc…--2200one row: Upper arm
GET/R6/BodyStructure/99dc…--2404rows don't exist in R6
PUT/R6/BodyStructure/99dc…200remove Forearm, so Upper arm moves into the primary row
GET/R4/BodyStructure/99dc…--2410old row is gone
GET/R4/Observation/o1200version 2, now references BodyStructure/99dc…

Rejected on R4 write 422

BodyStructure/99dc…--2/_history/1“can't be version-specific”
#bs1“can't reference a contained resource”
http://localhost:8080/R4/BodyStructure/99dc…“must be relative for this server”
Patient/d4ddfc62-…“must reference a BodyStructure”

These forms couldn't be translated to R6 or repointed safely, so they are refused up front. Whether the target exists isn't checked.

FMLObservation_4to6.fml + BodySiteReference_4to6.fml

// Observation: keep bodySite, without the reference extension
src.bodySite as s where (coding.exists() or text.exists() or …)
  -> tgt.bodySite as t then ObservationBodySite(s, t);

// … and turn each bodySite extension into an R6 bodyStructure
src.bodySite as b then {
  b.extension as e
      where (url = 'http://hl7.org/fhir/StructureDefinition/bodySite') then {
    e.value : Reference as r
      -> tgt.bodyStructure as cr, cr.reference as t
      then BodySiteReference(r, t);
  };
};

// Row reference → resource reference. No <<type+>>: it runs only
// when called by name, so other References are untouched.
group BodySiteReference(source src : ReferenceR4,
                        target tgt : ReferenceR6) extends Element {
  src.reference as r -> tgt.reference =
    (r.replaceMatches('^(BodyStructure/[^/]+)--[0-9]+$', '$1'));
  src.type       -> tgt.type;
  src.identifier -> tgt.identifier;
  src.display    -> tgt.display;
}

WatchProblems this creates, and what's still open

  • No R4 element to reference a BodyStructure. R4 core has none, so the standard bodySite extension carries it. R6 has Observation.bodyStructure.
  • Two identities. A row id is valid in R4 only; R6 needs the resource id. The map translates, and R6 can't say which structure was meant.
  • Rows move. Removing the first structure moves the next into the primary row and leaves a 410. Every referrer has to be found and rewritten in the same transaction, which creates new versions of resources nobody edited.
  • Only Observation, read-only in R6. Every other type that can point at a BodyStructure (Procedure, Condition, Specimen, ServiceRequest… via bodySite or the procedure extensions) needs the same map, check and repoint.
  • Writes through R6 aren't possible yet. An R6 Observation can't say which row it means, so there's no R6 → R4 map.
  • Design question: is splitting worth the reference cost, or should R4 keep one row with the extra structures in extensions?

7 / 7

Conclusion

Storing one version and projecting the other with FML works end to end. The generated maps run unchanged for reads. Writes need reverse maps and a decision on where R6-only data lives in R4.

What works today

Resource/R4/R6 read/R6 write
PatientCRUDyes405
EncounterCRUD + class, class-r6 searchyes + class search405
BodyStructureCRUDyesCRUD
ObservationCRUD, BodyStructure referencesyes, bodyStructure405
  • One FML engine: the FHIRPath Lab executor runs the 164 R4 → R6 maps (163 generated), including imports and extends.
  • R4 writes are validated against R4 4.0.1; R6 writes against R6 6.0.0-ballot5, plus a round-trip check.
  • Ids and versionId survive conversion, so an R6 response carries the same ETag as the stored R4 version.
  • 129 integration tests pass against PostgreSQL 18.

Patterns we found

  • Same shape (Patient): a generated one-to-one map is enough.
  • Renamed element (Encounter period → actualPeriod): handled by the generator.
  • 0..1 became 0..* (Encounter class, BodyStructure morphology): extra values go into an HL7-pattern cross-version extension (…/6.0/StructureDefinition/extension-…) on the R4 side, and the map folds them back.
  • A repeating group with no R4 equivalent (BodyStructure includedStructure): split into linked R4 rows. This is our own design, not HL7's, and needs server code beyond FML.
  • Splitting changes identity: references to a split resource must be translated (row → resource) on read, and repointed when rows move. FML handles the translation; the repointing is server code.
  • Search depends on the version: R4 class keeps its standard meaning, so values that only exist in R6 need a separate backport parameter (class-r6). The search runs on the stored R4; FML only converts the results.

RisksOpen issues

  • Silent loss on read: generated maps skip some elements (e.g. Encounter reasonCode), and the R6 view drops them without warning.
  • Draft maps: generated against R6-ballot5 and still carry review warnings. Local fixes (the 6.0 extension filter) still have to go into the generator.
  • No data migration: Encounters stored with the old xver/encounter-class URL lost their extra class in the R6 view.
  • Validation gaps: date formats and required code bindings are not checked yet.
  • References to BodyStructure work for Observation only. Other referrers (Procedure, Condition, Specimen, ServiceRequest…) still need the same map, checks and repointing, and R6 can't say which structure a reference meant.

Next steps

  • R6 → R4 maps for Patient and Encounter, so /R6 can accept writes.
