R4 and R6 resource maps

The server stores FHIR R4 and also serves the same data as R6. Some resources don't have the same shape in both versions, so one resource on one side can be several on the other. This page shows how those cases are mapped.

Everything below describes the working code. The tests named here are in test/bodystructure-r6.test.ts and test/bodystructure-cross-version.test.ts. R6 is pinned to the draft hl7.fhir.r6.core@6.0.0-ballot5.

BodyStructure: one R6 resource, several R4 rows

In R6, includedStructure repeats. In R4, location and morphology each hold one value. To keep every structure, each one becomes its own R4 resource. Our design, not defined by HL7

Each row is a normal, valid R4 resource, and R4 clients can read and change it directly. Rows show they belong together: a server-managed extension holds each row's position, secondary rows reference the primary row, and the primary row lists the others in order. An R4 client can find the whole group from any row. A group of one has no extension.

A row keeps its id while its structure exists, and numbers are never reused. R6 shows the row as includedStructure.id: "1" for the primary, "3" for abc--3. Row ids like abc--2 exist only in R4, so GET /R6/BodyStructure/abc--2 returns 404.

Field by field

copied merged into one element kept in an extension

Maps: fml-maps/R6_R4/maps/StructureMaps/BodyStructure_6to4.fml and fml-maps/R4_R6/maps/StructureMaps/BodyStructure_4to6.fml. … also covers image, language and text. Attachments are mapped field by field: height, width, frames, duration and pages become extensions, and size changes from an R6 string to an R4 number. Extensions we don't recognise are carried across: one on the R6 resource is wrapped and placed on every row, and one on a structure, or written on an R4 row, stays with that structure.

Reading through R6 runs the rows back through the other map. The result equals the request, plus the server-assigned includedStructure.id (test "fan-out"). The field extension URLs follow the pattern already used in the generated maps; the row link is this server's own.

What happens on each request

Every write, from either version, has to be valid in both before it commits. An R4 client therefore can't store something R6 can't read.

Any failure before the last step returns 422 and stores nothing. The code is in src/http/grouped.ts.

Hard cases

Shared field edited on any row

An R4 client changes description on abc--2. The value is copied to every row, so R6 shows it and no edit is lost.

tests 3, 4

Rows that move or disappear

R6 updates match rows by includedStructure.id, then by identical content. After abc--2 is deleted, a new structure gets --4, and --2 stays 410. Reordering changes positions, not ids.

tests 16–19

Removing the primary's structure

The R6 resource needs a row with its own id, so the first remaining structure moves into the primary row. This is the one case where a structure changes row.

test 20

What isn't there

excludedStructure stays an extension and is never a row, because a row would read as a structure that is present. It is on every row, so deleting a row can't lose it.

test 27

R4 client drops our extensions

A PUT with no extension array restores them from the stored row, so R6-only data survives clients that drop what they don't understand.

tests 5, 25, 26

R4 client removes one on purpose

A PUT with an extension array states the client's intent, so anything left out is removed. If no array would remain, send X-Replace-Extensions: true.

tests 23, 24

Laterality code removed on purpose

The marker sits on the code itself. If the client removes the code from locationQualifier, laterality goes too.

test 6

Stale R6 ETag

After an R4 edit of any row, an R6 PUT using the old If-Match gets 412 and overwrites nothing.

test 7

Valid in one version only

R4 without location can't become R6, and R6 without patient can't be stored as R4. Both return 422.

test 9, "no patient"

Deletes

Deleting abc--2 removes one structure. Deleting abc removes the whole group, because the R6 resource shares that id.

Known limits

  • R4 rows can still read as separate structures, while R6 describes one structure covering several regions. The row link connects them in both directions, but an R4 client has to look for it, and its example.org URL isn't a published definition.
  • Content the server can't carry safely returns 422 rather than being lost:
    • contained exists in both versions, but each embedded resource would need its own map.
    • implicitRules and modifierExtension can change what a resource means, and the server can't interpret them.
    • An R6 Attachment.size over 2,147,483,647 doesn't fit R4's unsignedInt.
    • Extensions using a URL the mapping relies on are reserved.
    • extension or id directly on landmark elements, and extensions on primitive values, aren't mapped yet.
    • Anything else that wouldn't survive conversion. Every write is converted and converted back, and a difference returns 422 naming the path. Examples are R6-only extension types like valueInteger64, and R6-only fields inside datatypes like Timing.repeat.startOffset.
  • X-Replace-Extensions is this server's own header, so a client has to know about it. A client that sends an extension array but leaves ours out of it removes them.
  • Decimal precision isn't kept: 2.0 comes back as 2, because JSON is parsed as JavaScript numbers. This applies to the whole server.
  • Search and history interactions aren't available for these resources.
  • R6 references to BodyStructure are mapped for Observation.bodyStructure only, as described below. Other types, such as Condition.bodyStructure, aren't mapped yet.

References to a BodyStructure

No core R4 element can reference a BodyStructure, but the standard http://hl7.org/fhir/StructureDefinition/bodySite extension can. R4 stores the reference there. R6 reads it as bodyStructure, and the extension isn't shown. R4 bodySite holds one value and R6 bodyStructure repeats, so several references means repeating the extension. Tests are in test/observation-bodystructure-reference.test.ts.

When a structure moves

If the first structure is removed through R6, the next one moves into the primary row and its old row returns 410. In the same transaction, every Observation that references the old row is changed to reference the primary row, and gets a new version. Nothing else rewrites references.

Continuing the example, a client removes Forearm with PUT /R6/BodyStructure/abc. Upper arm moves from abc--2 into abc, so Observation o1 is changed without its client doing anything:

What is rejected

An R4 create or update returns 422 if a bodySite extension on Observation.bodySite has no valueReference, or if its reference targets another type, is version-specific, points at a contained resource, or is an absolute URL on this server. Whether the target exists isn't checked, as with every other reference on this server.

R4: POST /R4/Observation 
"bodySite": {
  "extension": [{
    "url": "…/StructureDefinition/bodySite",
    "valueReference": {
      "reference": "Patient/example"
    }
  }]
}
Response: 422 
{
  "resourceType": "OperationOutcome",
  "issue": [{
    "severity": "error",
    "code": "invalid",
    "diagnostics": "Observation.bodySite
      .extension(…/StructureDefinition/bodySite)
      must reference a BodyStructure:
      Patient/example"
  }]
}

Limits

  • R6 can't tell which structure an R4 reference meant. It only shows the whole resource.
  • A reference to abc can change meaning in R4. After the first structure is removed, abc returns what used to be the second structure, with no error. abc can mean the whole resource or the first structure, so it can't be rewritten.
  • Deleting a referenced row leaves the R4 reference returning 410, and R6 still shows abc, now without that structure. Deleting the whole group leaves both returning 410.
  • References held outside this server, or as absolute URLs, aren't rewritten when a structure moves.
  • An Observation PUT sent without If-Match by a client holding an older copy can put the old row reference back. With If-Match it gets a 412.
  • Only Observation.bodySite is mapped. The same extension elsewhere on an Observation is copied to R6 unchanged, including any row id.
  • Observation is read-only through R6, so an R6 client can't write bodyStructure.

Adding another type

  1. Add the type to STORED_RESOURCE_TYPES and to BODY_SITE_REFERRERS in src/db/repository.ts.
  2. In its 4→6 map, consume the extension and call the shared BodySiteReference group, as Observation_4to6.fml does. R4 Condition, Procedure and ServiceRequest have a repeating bodySite, and Specimen and ImagingStudy nest theirs, so the rewrite and the checks, which read a single bodySite at the root, need extending for them.
  3. Call checkBodySiteReferences for the type in src/http/server.ts.

Writing maps for this engine

Maps run on the FHIRPath Lab executor in vendor/fhirpath-lab. It knows FHIR types and refuses to write a value across versions without a mapping, so every value goes through a datatype map. R4_R6 holds the generated ones, and R6_R4 holds the same files reversed.

GoalWrite thisNot this
Copy a value across versionssrc.a -> tgt.a;src.a as v -> tgt.a = v; is rejected for complex values
Fill a choice elementx.valueCodeableConcept as t then CodeableConcept(v, t)x.valueCodeableConcept = v
Read an extension's valuee.value : CodeableConcept -> tgt.a;e.value -> tgt.a; is ambiguous across all value types
Add a resource to a Bundlecreate('BodyStructure') as out, b.entry as e, e.resource = outcreate() with a uses alias
Reuse rules in two placesOne group per contextual typeOne group for a resource and an Extension
Convert a type differently in one placegroup X(source src : ReferenceR4, target tgt : ReferenceR6), called by name<<type+>> or <<types>>, which apply to every value of that type. Untyped parameters only work inside the file that calls the group

Open type groups must be unique per source type. Two <<type+>> groups for string make every valueString extension fail with "Ambiguous default mapping". Use <<types>> for a conversion to a specific other type.
