R4 and R6 resource maps

The server stores FHIR R4 and also serves the same data as R6. Some resources don't have the same shape in both versions: one resource or one element on one side can be several on the other. This page shows how those cases are mapped.

Everything below describes the working code. The BodyStructure tests named here are in test/bodystructure-r6.test.ts and test/bodystructure-cross-version.test.ts, the Encounter search tests in test/patient-r4.test.ts, and the Patient and Encounter write tests in test/r6-writes.test.ts. R6 is pinned to the draft hl7.fhir.r6.core@6.0.0-ballot5.

BodyStructure: one R6 resource, several R4 rows

In R6, includedStructure repeats. In R4, location and morphology each hold one value. To keep every structure, each one becomes its own R4 resource. Our design, not defined by HL7

Each row is a normal, valid R4 resource, and R4 clients can read and change it directly. Rows show they belong together: a server-managed extension holds each row's position, secondary rows reference the primary row, and the primary row lists the others in order. An R4 client can find the whole group from any row. A group of one has no extension.

A row keeps its id while its structure exists, and numbers are never reused. R6 shows the row as includedStructure.id: "1" for the primary, "3" for abc--3. Row ids like abc--2 exist only in R4, so GET /R6/BodyStructure/abc--2 returns 404.

Field by field

copied merged into one element kept in an extension

Maps: fml-maps/R6_R4/maps/StructureMaps/BodyStructure_6to4.fml and fml-maps/R4_R6/maps/StructureMaps/BodyStructure_4to6.fml. … also covers image, language and text. Attachments are mapped field by field: height, width, frames, duration and pages become extensions, and size changes from an R6 string to an R4 number. Extensions we don't recognise are carried across: one on the R6 resource is wrapped and placed on every row, and one on a structure, or written on an R4 row, stays with that structure.

What happens on each request

Every write, from either version, has to be valid in both before it commits. An R4 client therefore can't store something R6 can't read.

Any failure before the last step returns 422 and stores nothing. The code is in src/http/grouped.ts.

Hard cases

Shared field edited on any row

An R4 client changes description on abc--2. The value is copied to every row, so R6 shows it and no edit is lost.

Rows that move or disappear

R6 updates match rows by includedStructure.id, then by identical content. After abc--2 is deleted, a new structure gets --4, and --2 stays 410. Reordering changes positions, not ids.

tests 16–19

Removing the primary's structure

The R6 resource needs a row with its own id, so the first remaining structure moves into the primary row. This is the one case where a structure changes row.

test 20

What isn't there

excludedStructure stays an extension and is never a row, because a row would read as a structure that is present. It is on every row, so deleting a row can't lose it.

test 27

R4 client drops our extensions

A PUT with no extension array restores them from the stored row, so R6-only data survives clients that drop what they don't understand.

tests 5, 25, 26

R4 client removes one on purpose

A PUT with an extension array states the client's intent, so anything left out is removed. If no array would remain, send X-Replace-Extensions: true.

tests 23, 24

The marker sits on the code itself. If the client removes the code from locationQualifier, laterality goes too.

test 6

test 7

R4 without location can't become R6, and R6 without patient can't be stored as R4. Both return 422.

Known limits

  • R4 rows can still read as separate structures, while R6 describes one structure covering several regions. The row link connects them in both directions, but an R4 client has to look for it, and its example.org URL isn't a published definition.
  • Content the server can't carry safely returns 422 rather than being lost:
    • contained exists in both versions, but each embedded resource would need its own map.
    • implicitRules and modifierExtension can change what a resource means, and the server can't interpret them.
    • An R6 Attachment.size over 2,147,483,647 doesn't fit R4's unsignedInt.
    • Extensions using a URL the mapping relies on are reserved.
    • extension or id directly on landmark elements, and extensions on primitive values, aren't mapped yet.
    • Anything else that wouldn't survive conversion. Every write is converted and converted back, and a difference returns 422 naming the path. Examples are R6-only extension types like valueInteger64, and R6-only fields inside datatypes like Timing.repeat.startOffset.
  • X-Replace-Extensions is this server's own header, so a client has to know about it. A client that sends an extension array but leaves ours out of it removes them.
  • Decimal precision isn't kept: 2.0 comes back as 2, because JSON is parsed as JavaScript numbers. This applies to the whole server.
  • Search and history interactions aren't available for these resources.
  • R6 references to BodyStructure are mapped for Observation.bodyStructure only, as described below. Other types, such as Condition.bodyStructure, aren't mapped yet.

Encounter.class: one value in R4, several in R6

R4 Encounter.class is one Coding and required (1..1). R6 Encounter.class is a list of CodeableConcepts (0..*). The first class stays in the R4 element. Every further class goes into its own extension with the URL http://hl7.org/fhir/6.0/StructureDefinition/extension-Encounter.class, the pattern BodyStructure uses as well. URL pattern stated by HL7

Encounter.class search: the R6 meaning on R4

An R4 client that searches class gets the R4 meaning: the one native Coding. To give R4 clients the R6 meaning as well, the server adds a second parameter, class-r6. It matches the native class and every class extension, on the resource and on R4 class, the same Encounters /R6 finds, but returns the stored R4 resources.

RequestMatchesReturnsFinds the example for …|VR
GET /R4/Encounter?class=native class onlyR4no
GET /R4/Encounter?class-r6=native class and class extensionsR4, as storedyes
GET /R6/Encounter?class=same as class-r6R6, through FML 4→6yes

As FHIRPath, class-r6 evaluates:

Encounter.class
  | Encounter.class.extension('http://hl7.org/fhir/6.0/StructureDefinition/extension-Encounter.class').value
  | Encounter.extension('http://hl7.org/fhir/6.0/StructureDefinition/extension-Encounter.class').value

Why a second name. R4 forbids changing class: "Parameter names cannot overlap with standard parameter names, and standard parameters cannot be redefined" (CapabilityStatement.rest.resource.searchParam.name). A client that knows only R4 therefore gets exactly the R4 behaviour, and the backport is opt-in.

Why this definition URL. The CapabilityStatement lists class-r6 with the definition http://example.org/fhir/SearchParameter/Encounter-class-r6. Our design, not defined by HL7 It is an R4 SearchParameter in fhir/r4/SearchParameter-Encounter-class-r6.json, loaded by the canonical manager next to the R4 core package and served at /R4/SearchParameter/Encounter-class-r6. Its expression is the one above. example.org is a placeholder; HL7 publishes no such parameter, so it isn't under hl7.org.

Code: src/http/server.ts (ENCOUNTER_SEARCH_PARAMS, encounterSearchParams) and searchEncounterClass in src/db/repository.ts. Token syntax for all three: code, system|code, |code or system|.

Encounter: hard cases and limits

Native and extension both match

The Encounter is returned once, through class-r6 on R4 and class on R6.

"class-r6 backports …", "… returned once"

System and code from different codings

system|code has to match within one Coding. A system from one coding and a code from another don't match.

"class search finds extension codings …"

Other extensions

Only the class extension URL counts. An extension with another URL that holds the same code doesn't match.

"class-r6 backports …"

class and class-r6 together

400 with an OperationOutcome. Each request takes one class parameter.

"unsupported and malformed class queries …"

class-r6 on /R6

400. In R6, class already has this meaning, so the R6 CapabilityStatement lists only class.

"R6 metadata advertises …"

R4 read and write

R4 returns the stored extension unchanged, and the native class stays required, so every Encounter has a first class.

"create and read preserve …", "R4 class remains required"
  • HL7 doesn't say whether the extension holds every class or only the ones beyond the native element. Here it holds only the additional ones, so an extension that repeats the native class shows up twice in R6.
  • The SearchParameter's expression documents the search; the server doesn't evaluate it. The SQL in src/db/repository.ts implements the same rule.
  • One token per request, as for class: comma lists, repeated parameters and modifiers return 400, and there is no pagination.
  • R4 class is one Coding. If the first R6 class has several codings or a text, R4 class gets its first coding, and the whole first class is also kept in the class extension on R4 class (the extension's context allows Encounter.class). R6 reads it from there.
  • The 6.0 part of the extension filter is a local change to the generated maps and still has to go upstream to the map generator.

Patient and Encounter: writes through R6

Patient and Encounter are stored as one R4 resource each, and /R6 can create, update and delete them. A write runs the R6_R4 map. It is stored only if the body is valid R6, the result is valid R4, and the result maps back through R4_R6 to the same content. An R6 client therefore never loses data without being told. Our design, the same rule as BodyStructure

What R4 has an element for goes there. Everything else uses HL7's cross-version extension pattern, so each version sees all of the data: R6-only content becomes http://hl7.org/fhir/6.0/StructureDefinition/extension-<element> in R4, and R4-only content becomes http://hl7.org/fhir/4.0/StructureDefinition/extension-<element> in R6. Each map reads back what the other wrote. Extension pattern stated by HL7

"Same content" ignores the order of lists, except where FHIR gives the order a meaning (orderMeaning): HumanName.given, prefix, suffix and Address.line. R4 keeps native values first and extensions after them, so other lists may come back reordered.

Encounter.status: different codes in R4 and R6

R6 renamed some statuses and moved arrived and triaged out of status into subjectStatus. The codes follow HL7's ConceptMaps R4-EncounterStatus-R5 and R5-EncounterStatus-R4, because R5 and R6 share them. Both directions use them, so reads changed too: finished, onleave, arrived and triaged used to be copied into R6 unchanged, as invalid codes. Codes from HL7's ConceptMaps subjectStatus for arrived and triaged is our design

status has a required binding, and R6 has more codes than R4. HL7's rule: the closest R4 code goes in the element, and the R6 code in the cross-version extension on the element (_status), so it comes back unchanged.

R6Stored R4Read back as R6
planned, in-progress, cancelled, entered-in-error, unknownthe same codethe same
on-holdonleaveon-hold
completedfinishedcompleted
dischargedfinished, and discharged in the status extensiondischarged
in-progress with subjectStatus arrived or triagedarrived or triagedthe same
discontinued422 for now: HL7's ConceptMap has no R4 code for it

TODO, values without an R4 mapping: discontinued, and Quantity.comparator ~ and ad. When a required binding has more codes in R6 and a value can't be mapped, the R4 value alone doesn't carry the meaning. The intended handling is a placeholder R4 code, the R6 code in the cross-version extension, and implicitRules on the resource. Until then these writes return 422. subjectStatus uses http://terminology.hl7.org/CodeSystem/encounter-subject-status; other subject statuses, such as departed, are kept in a 6.0 extension.

Patient and Encounter: hard cases and limits

R6-only content

Encounter.businessStatus or Patient.contact.role has no R4 element. It is stored in a 6.0 extension, and R6 reads it back.

"R6-only and multi-valued content …", "R6-only contact elements …"

R4-only history

R4 statusHistory reads in R6 as a 4.0 extension. An R6 PUT without an extension array keeps it; one that sends the array without it removes it.

"R4-only history reads as …"

Content only R4 shows

diagnosis.rank has no R6 place and no extension. An R6 PUT would remove it, so it returns 409 and the stored resource stays as it is.

"an R6 update can't remove …"

Reference targets

An R6 basedOn to a CarePlan, or a Patient as participant.actor, isn't allowed there in R4. It goes in an extension instead of an invalid R4 reference.

"references to targets R4 doesn't allow …"

Valid in R6, not in R4

An R6 Encounter without class is valid, but R4 requires one. 422, and the first issue says it is about the stored R4 form.

"valid R6 without class …"

Extensions the maps use

An R6 client that sends the class extension itself would turn it into an extra class. The round trip shows the difference, and the write returns 422.

"what R4 still can't hold …"

Stale ETag

An R6 PUT with an old If-Match gets 412, as through R4. Both versions share the version id.

"create, read through both versions …"
  • R4 writes aren't checked against R6, unlike BodyStructure. R4 clients keep everything R4 allows.
  • Still 422: the values without an R4 mapping (see the TODO above), an Encounter without class, and virtualService.addressExtendedContactDetail.
  • The R4 validator checks neither required bindings nor reference targets. The maps keep both within what R4 allows. The server checks the FHIR JSON form for primitive extensions (_status) itself, because the validator doesn't know it.
  • meta.profile and meta.source from an R6 body aren't kept: profiles are version-specific, and the server owns the rest of meta.
  • Like the rest of the server, decimals lose trailing zeros.

No core R4 element can reference a BodyStructure, but the standard http://hl7.org/fhir/StructureDefinition/bodySite extension can. R4 stores the reference there. R6 reads it as bodyStructure, and the extension isn't shown. R4 bodySite holds one value and R6 bodyStructure repeats, so several references means repeating the extension. When a structure moves

If the first structure is removed through R6, the next one moves into the primary row and its old row returns 410. In the same transaction, every Observation that references the old row is changed to reference the primary row, and gets a new version. Nothing else rewrites references.

What is rejected

An R4 create or update returns 422 if a bodySite extension on Observation.bodySite has no valueReference, or if its reference targets another type, is version-specific, points at a contained resource, or is an absolute URL on this server. Whether the target exists isn't checked, as with every other reference on this server.

R4: POST /R4/Observation 
"bodySite": {
  "extension": [{
    "url": "…/StructureDefinition/bodySite",
    "valueReference": {
      "reference": "Patient/example"
    }
  }]
}
Response: 422 
{
  "resourceType": "OperationOutcome",
  "issue": [{
    "severity": "error",
    "code": "invalid",
    "diagnostics": "Observation.bodySite
      .extension(…/StructureDefinition/bodySite)
      must reference a BodyStructure:
      Patient/example"
  }]
}

The other direction: an Observation written through R6

The examples so far start in R4. An R6 client writes bodyStructure instead, and the server stores each reference as a bodySite extension, because R4 storage has nowhere else to put it. bodySite holds one value in R4, so two references means two extensions on the same element, next to the text.

  "status": "final",
  "code": { "text": "Skin temperature" },
  "valueQuantity": { "value": 33.2, "unit": "Cel" },
  "bodySite": { "text": "Upper arm" },
  "bodyStructure": [
    { "reference": {
        "reference": "BodyStructure/abc" } },
    { "reference": {
        "reference": "BodyStructure/def" } }
  ]
}

  "id": "o2",
  "status": "final",
  "code": { "text": "Skin temperature" },

An R6 update doesn't widen a row reference

R6 can only reference the whole resource, so an R6 write on its own always stores abc. If R4 already stored a row reference, an R6 client sees abc and sends abc back. The server keeps the stored row reference, so an edit through R6 doesn't lose which structure was meant.

3PUT /R6/Observation/o3 with BodyStructure/abc and "status": "amended"BodyStructure/abc--2, version 2, status amended
4PUT /R6/Observation/o3 without bodyStructureNo reference, version 3. bodySite keeps its text

What R6 can't write

A row id doesn't exist in R6, and R4 has no place for a concept in bodyStructure. Both return 422 with nothing stored.

R6: a row id

  "reference": {
    "reference": "BodyStructure/abc--2"
  }
}]
Response: 422 
"diagnostics": "Not supported across FHIR versions
  yet: Observation.bodyStructure[0]
  .reference.reference"
R6: a concept 
"bodyStructure": [{
  "concept": { "text": "Left arm" }
}]
Response: 422 
"diagnostics": "Not supported across FHIR versions
  yet: Observation.bodyStructure"

Limits

  • R6 can't tell which structure an R4 reference meant. It only shows the whole resource.
  • A reference to abc can change meaning in R4. After the first structure is removed, abc returns what used to be the second structure, with no error. abc can mean the whole resource or the first structure, so it can't be rewritten.
  • Deleting a referenced row leaves the R4 reference returning 410, and R6 still shows abc, now without that structure. Deleting the whole group leaves both returning 410.
  • References held outside this server, or as absolute URLs, aren't rewritten when a structure moves.
  • An Observation PUT sent without If-Match by a client holding an older copy can put the old row reference back. With If-Match it gets a 412.
  • Only Observation.bodySite is mapped. The same extension elsewhere on an Observation is copied to R6 unchanged, including any row id.
  • bodyStructure.concept returns 422. Storing it apart from the references couldn't keep the order of a mixed list.
  • Keeping a row reference reads the stored Observation outside the write transaction, so a concurrent R6 PUT without If-Match can use a stale copy.

Adding another type

  1. Add the type to STORED_RESOURCE_TYPES and to BODY_SITE_REFERRERS in src/db/repository.ts.
  2. In its 4→6 map, consume the extension and call the shared BodySiteReference group, as Observation_4to6.fml does. R4 Condition, Procedure and ServiceRequest have a repeating bodySite, and Specimen and ImagingStudy nest theirs, so the rewrite and the checks, which read a single bodySite at the root, need extending for them.
  3. Call bodySiteReferenceProblem on its writes, as src/http/observation.ts does.

Observation: writable through both versions

One R6 Observation is one R4 row, so there is no grouping. Every write, from either version, must be valid in both, and anything that wouldn't survive the conversion returns 422 rather than being lost. The code is in src/http/observation.ts and src/fhir/observation.ts, the map back is Observation_6to4.fml, and the tests are in test/observation-crud.test.ts.

An R4 update that leaves out our extensions

It works like BodyStructure. No extension array means the client dropped what it doesn't understand, so ours come back, on the resource, on bodySite, and on referenceRange and component items that are otherwise unchanged. An array states the client's intent, and X-Replace-Extensions: true removes them. Leaving out bodySite altogether removes it and its references.

Limits

  • contained returns 422 through both versions, because the engine can't copy a resource across versions. R4 writes accepted it before R6 writes existed.
  • modifierExtension and implicitRules return 422 through both versions, because they can change what a resource means and the server can't interpret them.
  • Timing.repeat returns 422 from the validator through both versions, before any mapping runs. This isn't specific to Observation. Extensions on primitive values (_status) are accepted: the server checks that form itself, because the validator doesn't know it.
  • A valueSampledData interval must be in milliseconds, because R4 period is. Other units return 422.
  • Reference targets aren't checked against the version. R6 subject: Organization/1 is stored even though R4 doesn't allow that target, and R4 derivedFrom: Media/1 is returned through R6 even though R6 has no Media.
